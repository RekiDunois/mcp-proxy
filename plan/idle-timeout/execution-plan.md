# Idle backend shutdown execution plan

Revision R1, 2026-10-24. Baseline master 25a9b449286b00968838cfbc27c9969628745e6c. Independently approved; see plan-review.md. Implementation/results approval is separate.

## Scope

Add per-backend `idleTimeout` duration, omitted/zero disabled. Positive values require `lazyStart: true`; existing duration validation rejects negative/sub-millisecond values. No global inheritance, new lifecycle framework, arbitrary application session migration, deployment or merge. Stdio teardown terminates the owned process; remote transports only close this proxy's connection, not the remote service. Opting in permits loss of backend in-memory session/model state, subscriptions and unfinished asynchronous work outside an active forwarded request. Persistent data belongs to the backend. The next request reuses existing initialize/catalog registration. Frontend connections and routes remain.

## Implementation

Extend the existing lazy coordinator with active-use count, last-use/deadline timer and an idle-close completion channel. Acquire activity before activation/forwarding; cancel a caller's wait without canceling shared startup. On request completion set idle deadline. Timer checks ready and healthOK (never reclassify a confirmed live failure as an intentional idle stop), no active work, exact deadline/generation and live gateway. It atomically marks closing before releasing the lifecycle lock, then uses existing connectMu and closeTransport. Requests arriving during close wait for completion before one shared activation. Successful close forgets raw, resets the lazy activation epoch (everReady/retry state) and health to dormant; failed/uncertain close retains terminal cleanup error and never constructs another process. Activation success with no active caller always arms a fresh idle deadline (including when all startup waiters canceled); probe completion always rechecks/arms the original user deadline without refreshing it, so a timer skipped during starting/probing cannot leave a resident backend permanently. Close/shutdown cancels timers and serializes teardown; configuration changes require a gateway restart (there is no hot-reload path in main.go); the old instance uses existing Close/shutdown.

HTTP middleware is not sufficient for work lifetime: mcp-go SSE POST dispatches asynchronously and a GET stream stays open indefinitely. Count non-GET HTTP handlers and separately lease every actual forwarded tool, prompt and resource call (acquire before reading raw pointer, release after result/error). A GET triggers lazy startup but does not keep the backend resident for the stream lifetime. An asynchronous dispatch after HTTP return acquires its own lease and, if needed, waits for/restarts a dormant backend before using it. Catalog/local HTTP activity refreshes idle time; health probes never do. No payload inspection, request ID bookkeeping or protocol hooks are needed.

Keepalive skips dormant/closing/starting idle-enabled backends; lease active probes without refreshing user idle time, and coordinate probe result/reconnect decision with idle transition so a stale probe cannot wake a deliberately stopped backend. Recheck activity when applying probe failures and again under lazy.mu when starting reconnect; if a business request arrived meanwhile, defer recovery rather than close its transport. Starting reconnect clears ready under the same lock so later activity waits for that attempt. Skip probes while business work is in flight on idle-enabled backends to prevent long requests causing reconnect. Existing eager/lazy-disabled recovery remains unchanged. Live failure uses existing autoReconnect policy; an intentional idle stop begins a fresh lazy activation epoch even when autoReconnect is false.

Update configuration/usage and repository guidance with examples, scope and state-loss caveat. Preserve old lazy-start plans as historical records; this directory contains the sole current idle feature plan pair and concise results.

## Source evidence and alternatives

At baseline 25a9b44, client.go:connect/Close own connectMu, raw ownership, close-before-replacement and terminal cleanupErr; lazy.go:ensureStarted/startLocked own shared activation and retry epoch; http.go:startHTTPServer owns authenticated route mounting, readiness and shutdown. main.go loads config once, so no new hot reconfiguration API is added. Dependency github.com/mark3labs/mcp-go v1.1.0 server/sse.go:handleMessage launches HandleMessage in a goroutine after HTTP 202, while SSE GET remains open. Its client/transport/stdio.go:Close closes streams, waits/reaps and escalates termination; transport errors other than reaped exec.ExitError must retain the existing cleanup-uncertain prohibition.

Alternatives: counting HTTP lifetime alone either pins SSE forever or misses asynchronous work. Protocol hook/request-ID bookkeeping adds a separate dispatcher pairing contract unnecessarily when all downstream business forwarding already has three owned call sites. A generic process manager or application session snapshot expands scope and cannot preserve arbitrary MCP application state. Extend the existing lazy coordinator and raw close owner instead.
